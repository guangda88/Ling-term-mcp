## 五、四项高价值功能的灵元1.0拆解（薄主干+插片）

> 方法论：找到什么不变 → 砍到最薄 → 变化变成插片
> 灰区校验：前置（最低）→ 中间（回滚）→ 后置（修复）
> 主干：2T3A = records(在) + events(变) + create/query/transition

### 5.1 Tasks — 异步任务状态追踪

| 拆解维度            | 现有状态                                                                               | 目标态                |
| ------------------- | -------------------------------------------------------------------------------------- | --------------------- |
| **不变（records）** | `record_id, type, data, state, parent_id, created_by, created_at` 已在灵信 lm\_\* 工具 | 复用零迁移            |
| **变（events）**    | 任务进度需要新增 `progress_pct, eta, last_heartbeat` 三个字段                          | data 字段消化，不改表 |
| **主干**            | 灵信 lm_create / lm_transition 已支持自定义 type=task                                  | 零代码                |
| **插片**            | 新增 3 个 task 专用插片                                                                | 业务逻辑全在插片      |
| **灰区校验**        | 前置：白名单调用者；中间：超时未心跳自动 escalate；后置：审计日志                      | 全链路覆盖            |

**落地最小动作单元 (≤4 步)**:

1. `lm_create(type="task", data={progress:0, eta:null, heartbeat:now})` 创建任务记录
2. 定时插片 `transition(event_type="heartbeat", data={progress:n})` 更新进度
3. 中间件插片检测 5min 无心跳 → 灰区 escalate
4. `lm_query(parent_id=task_id)` 拉取完整流转链

**推广推力**: 灵犀现有会话最长 60min 超时即丢，Tasks 解决此痛点；lingresearch 已用类似机制，可直接复用模式。
**降低阻力**: 工具集零新增（4 步都用灵信 lm\_\*），文档新增 1 段使用示例即可。

### 5.2 OAuth 统一认证

| 拆解维度            | 现有状态                                                                        | 目标态       |
| ------------------- | ------------------------------------------------------------------------------- | ------------ |
| **不变（records）** | 灵族成员身份表（12 成员 + KNOWN_INFRASTRUCTURE）                                | 不变         |
| **变（events）**    | 当前用 caller 字符串白名单 → 改为 OAuth token 验证                              | 校验方式变   |
| **主干**            | 身份白名单 + 签名 + 治理三件套                                                  | 不动         |
| **插片**            | 新增 OAuth2 适配层（Entra/Okta/标准 OAuth）                                     | 业务插片     |
| **灰区校验**        | 前置：token 校验 + scope 校验；中间：scope 不足 escalate；后置：审计 token 来源 | 前置最低成本 |

**落地最小动作单元 (≤4 步)**:

1. 在 `src/security/identity.ts` 新增 `verifyOAuthToken(token, scope)` 插片
2. execute_command 入口前置校验：白名单 ∪ OAuth 都通过
3. 中间插片：scope 不足 → 自动 escalate 到治理
4. audit_report 增列：oauth_used=true 维度统计

**推广推力**: 与外部 MCP 互操作需要标准认证；OAuth 是 Anthropic/MCP 官方推荐
**降低阻力**: 现有白名单保留为 fallback，不破坏现有调用

### 5.3 Tunnels 跨网穿透

| 拆解维度            | 现有状态                                                                    | 目标态           |
| ------------------- | --------------------------------------------------------------------------- | ---------------- |
| **不变（records）** | 灵族成员路径表（/home/ai/\* 固定）                                          | 不变             |
| **变（events）**    | 当前直连 / SSH / 反向代理混合                                               | 统一 Tunnel 协议 |
| **主干**            | 灵信 LingBus（HTTP 中继）已实现跨项目                                       | 复用为主干       |
| **插片**            | 新增 Tunnel 适配层（wireguard/cloudflared/自研）                            | 业务插片         |
| **灰区校验**        | 前置：成员身份 + Tunnel 白名单；中间：流量异常 escalate；后置：审计每条连接 | 全覆盖           |

**落地最小动作单元 (≤4 步)**:

1. zhibridge 已有 HTTP 中继主干 → 在 `/home/ai/zhibridge/` 新增 `tunnel_adapter.py` 插片
2. LingBus 消息新增 `via_tunnel=true` 元数据
3. 前置校验：成员身份 + Tunnel 注册表（独立白名单文件）
4. visible_state 增列 tunnel_active_count 维度

**推广推力**: 灵族分布式（成员在不同机器/容器），Tunnel 解决跨网直接调用痛点；与灵信中继互补
**降低阻力**: 复用 zhibridge 现有主干，不引入新依赖

### 5.4 仪表盘观测

| 拆解维度            | 现有状态                                                         | 目标态       |
| ------------------- | ---------------------------------------------------------------- | ------------ |
| **不变（records）** | audit_report + visible_state 7 维度数据                          | 不变         |
| **变（events）**    | 当前 JSON 输出人工解读 → 仪表盘实时渲染                          | 渲染变       |
| **主干**            | 灵犀 visible_state_check + audit_report 两个工具                 | 不动         |
| **插片**            | 新增可视化前端（灵网 HTML/Chart.js 或灵克 Plot）                 | 纯插片       |
| **灰区校验**        | 前置：调用者必须是仪表盘读权限；中间：数据脱敏；后置：审计读访问 | 前置最低成本 |

**落地最小动作单元 (≤4 步)**:

1. 灵网 `/api/visible` 已聚合灵信数据 → 复用
2. 新增 `dashboard.html` 静态页面（Chart.js CDN）
3. 前置：仪表盘读权限加入成员白名单子集（read-only 角色）
4. audit_report 增列 dashboard_views 维度

**推广推力**: 现状可视化能直接暴露工具欠用情况（如 visible_state 调用次数低），推广有数据支撑
**降低阻力**: 复用灵网现有 API，无新后端；前端纯静态

## 六、推广推力 vs 阻力 总结

| 功能    | 推力                                    | 阻力                         | 优先级 |
| ------- | --------------------------------------- | ---------------------------- | ------ |
| Tasks   | 解决会话超时痛点；lingresearch 已有模式 | 文档缺；插片零个             | **P0** |
| 仪表盘  | 数据已就绪；可视化直接驱动推广          | 前端需 1 人天                | **P1** |
| OAuth   | 外部互操作刚需                          | 现有白名单已用，无紧迫感     | **P2** |
| Tunnels | 分布式场景刚需                          | 涉及网络安全，灰区校验成本高 | **P3** |

**核心结论**: 4 功能按灵元1.0拆解后，每个都是 0 新主干 + 1~2 插片 + 灰区校验全覆盖。最大推广推力来自 **Tasks**——直接解决现有痛点且零新代码。
